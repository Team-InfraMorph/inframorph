# 전체 실행 흐름과 중단 범위

## 최초 배포의 흐름 {#pipeline}

```text
소스 수집·분석 생성
  → G-002 지원 소스·분석 대조
  → I-000 → I-001 → I-006 → I-003 → I-004 → I-002
  → 대상 설계 생성 → G-003 → L-001 → L-002
  → 대상별 패치 생성
  → P-001 → P-006 → P-007 → P-002 → P-003 → P-004 → P-005
  → 빌드 직전 패치 재검사 → X-001 → 이미지 빌드
  → 이미지·설계 연결 확인 → 대상 실행 → 상태·접속 검증
```

이 순서는 규칙 ID 숫자순과 다릅니다. G-003은 Local worker의 patch/build/deploy 진입에서도 반복됩니다. 스냅샷 검증·모델 파싱·판정 저장 같은 규칙 밖 경계도 있으며, 거기서 실패하면 규칙 실행 기록이 없을 수 있습니다.

| 지점 | 입력과 통과 후 자료 | 실패 시 영향 | 다시 시작 |
|---|---|---|---|
| 공통 분석·설계 준비 | 동일 snapshot/RepoMap → 검사된 Intent·대상 Plan | runtime.prepare에서 실패하면 대상 worker 시작 전 전체 준비 중단 | 실제 소스와 분석·설계 수정 후 준비부터 |
| Local 대상 실행 | 보존 context → 소스/분석 재검사 → 패치 승인 | 해당 Local 경로의 이후 빌드·실행 중단 | 새 패치 또는 입력으로 해당 정상 배포 |
| AWS 대상 실행 | 보존 context → Intent/Plan/패치 검사·빌드 | 해당 AWS 경로의 후속 클라우드 작업 중단 | 원인 수정 후 AWS 배포 경로 |
| 빌드 | 검증된 패치 메모리 바이트 → 이미지 식별값 | 이미지 생성 또는 후속 실행 진행 불가 | 묶음과 프로필 재검사부터 |
| 실행·접속 확인 | 이미지와 대상 환경 → 관측된 결과 | 환경 오류·복구 경로, 정책 위반으로 자동 분류 안 함 | 배포 환경과 복구 기록 확인 |

대상 worker가 시작된 뒤에는 orchestrator가 대상을 별도 스레드로 실행합니다. 한 대상 실패가 이미 성공한 다른 대상을 자동 취소한다는 보장은 없습니다. 대상별 상태와 전체 상태를 함께 읽습니다.

## 반복 검사의 이유 {#checkpoints}

분석 직후 확인한 소스가 패치 직전에도 같은지, 패치 승인 뒤 Builder가 같은 내용을 쓰는지 다시 확인합니다. 같은 규칙도 실행 ID와 checkpoint가 다르면 별도 검사입니다. 이벤트 61건은 규칙 61종 또는 독립 배포 61번이 아닙니다.

## 실패·복구·재검사의 차이 {#recovery}

- 첫 검사 예외는 남은 규칙을 실행하지 않습니다. 남은 항목은 NOT_RUN이며 별도 악성 행위 판정이 아닙니다.
- Local 실행 검증 실패 뒤 복구 경로는 원인 분석·수정 후보·정책 검사·빌드·재검증을 다시 수행할 수 있습니다. 초기 정책 차단을 자동 면제하는 흐름은 아닙니다.
- 정책 업데이트 재검사는 저장된 snapshot·Intent·Plan·bundle·이미지 식별 연결을 확인하고 기존 검사 함수를 재실행합니다. 모델 호출·빌드·재배포·현재 클라우드 조회를 하지 않습니다.
- 자료가 없거나 변했다면 재검사 불가입니다. 최신 branch로 바꿔 검사한 결과를 과거 배포의 결과로 쓰지 않습니다.
- 기존 실행 서비스는 문서 갱신이나 재검사 실패만으로 자동 중단하지 않습니다.

## 규칙 밖 경계 {#boundaries}

필수 판정 저장 실패는 다음 실행을 막습니다. 진단 로그 저장 실패는 별도의 경고입니다. snapshot/patch/image의 fingerprint, 정책 guard, 소스·artifact schema 실패는 규칙 내부 판정과 실행 전제 오류를 구분해 봅니다. 기록이 없으면 성공으로 추정하지 않습니다.
