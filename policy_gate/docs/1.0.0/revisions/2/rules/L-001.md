# L-001 · 설계 형식

정책 1.0.0 · 규칙 revision 1 · 문서 revision 2

## 목적 {#purpose}

실행 대상·서비스·저장 형태가 Plan 계약을 만족하는지 확인합니다. 이후 관계 검사의 안전한 입력을 만듭니다.

## 입력과 적용 조건 {#inputs}

Intent와 Plan 전체. validate_plan 진입에서 두 스키마를 파싱합니다. 다른 진입점의 사전 파싱에서 먼저 실패할 수도 있습니다.

## 처리 과정 {#procedure}

1. Intent·Plan을 모델 계약으로 파싱하고 알 수 없는 필드와 잘못된 값을 거부합니다.
2. Plan 스키마는 image_tag=app:<source_revision>, 서비스 이름 중복 없음, 공개 HTTP 정확히 하나를 요구합니다.
3. worker는 명령이 있고 비공개이며 port/health가 없어야 합니다. HTTP는 유효 포트와 /로 시작하는 health 경로가 필요합니다.
4. Local/AWS별 DB·저장 타입, 로그, STORAGE_DRIVER 및 DB 사용 시 DATABASE_URL 이름 조건을 확인합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| schema_invalid | BLOCK | validate_plan 내부 모델 계약 위반 | 서비스·대상·저장·이미지 태그를 계약에 맞게 수정합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

성공 파싱 뒤 source_revision·target, 실행 binding의 intent_digest·plan_digest를 남깁니다. 실제 네트워크 관측은 없습니다.

## 해결과 재검증 {#remedy}

1. Plan의 대상과 서비스 공개 설정부터 확인합니다.
2. 분석이 맞으면 Planner 출력과 생성 로직을 수정합니다.
3. L-001 뒤 L-002와 G-003을 함께 통과해야 실행할 수 있습니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 공개 web 하나와 비공개 worker | PASS |
| 위반 | 공개 worker 또는 공개 HTTP 둘 | BLOCK |
| 경계 | HTTP port=65535 | 스키마 범위 안; demo 프로필은 3000 요구 |
| 오류 | 모델 파싱 이전 호출부 예외 | 그 호출 단계 오류; 이 규칙 실행을 꾸며내지 않음 |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.
