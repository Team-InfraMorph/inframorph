# P-003 · Prisma 구조 보존

정책 1.0.0 · 규칙 revision 1 · 문서 revision 2

## 목적 {#purpose}

DB provider 전환에 무관한 모델·필드·기본값·지시문 변경이 섞이지 않게 합니다.

## 입력과 적용 조건 {#inputs}

prisma/schema.prisma가 변경되었을 때 원본·결과 스키마와 Plan.db를 사용합니다. 미변경이면 schema_unchanged로 적용 제외합니다.

## 처리 과정 {#procedure}

1. 원본 스키마가 있고 Plan.db가 있는지 확인합니다.
2. 주석·공백을 제외하고 제한된 Prisma 토큰 구조를 읽습니다. 지원 datasource provider만 가려 비교합니다.
3. provider를 제외한 전체 토큰 목록이 같아야 합니다.
4. 변환 후 provider가 postgresql인지 확인합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| prisma_transform_unsupported / prisma_structure_unsupported | UNSUPPORTED | 지원 전제·구조 밖 | 스키마와 변환 범위를 별도 검토합니다. |
| prisma_structure_changed | BLOCK | provider 외 구조 변경 | 모델 변경을 배포 패치에서 제거하고 앱 변경으로 검토합니다. |
| prisma_provider_invalid | BLOCK | 결과 provider가 postgresql이 아님 | 계획된 provider 전환을 정확히 생성합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

path·before·after provider를 기록합니다. 전체 모델 차이는 패치 diff에서 확인합니다.

## 해결과 재검증 {#remedy}

1. provider 변경과 스키마 구조 변경을 구분합니다.
2. 실제 모델 변경이 필요하면 별도의 소스·데이터 마이그레이션 작업으로 처리합니다.
3. 패치 검사를 다시 실행합니다. 통과 후에도 데이터 이전 검증은 별개입니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | sqlite → postgresql만 변경 | PASS |
| 위반 | 필드 또는 @unique 추가 | BLOCK |
| 경계 | 스키마 파일 미변경 | NOT_APPLICABLE |
| 미지원 | 여러 datasource 또는 지원 밖 구문 | UNSUPPORTED |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.

## 한계와 관련 검사 {#limits}

전체 Prisma 언어 AST나 데이터 마이그레이션 검증이 아닙니다. 주석·공백만 변경해도 변경 파일로 분류되며 결과 provider가 sqlite이면 차단될 수 있습니다.
