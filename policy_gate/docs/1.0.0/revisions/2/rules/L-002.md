# L-002 · 분석과 설계 일치

정책 1.0.0 · 규칙 revision 1 · 문서 revision 2

## 목적 {#purpose}

형식상 유효한 Plan이 실제 Intent와 다른 앱·worker·저장·비밀정보를 추가하거나 누락하지 않게 합니다.

## 입력과 적용 조건 {#inputs}

L-001에서 파싱된 Intent·Plan, 서비스·state·secrets·config. Plan 전체 형식과 관계를 분리하여 검사합니다.

## 처리 과정 {#procedure}

1. Plan의 일반 설정에 비밀 이름 충돌·금지 설정 검사를 적용합니다.
2. commit·앱과 서비스의 name/kind/public/port/health/command 집합이 분석과 같은지 비교합니다.
3. DB·파일 저장의 존재와 저장 경로를 비교합니다. 저장 요구는 하나까지만 관계 검사에서 허용합니다.
4. 필요 비밀 이름 집합 및 config 보존을 확인합니다. 추가 config는 PORT·STORAGE_DRIVER만 허용합니다.
5. 예약 서비스 이름 db/schema/tunnel과 CPU 4096·메모리 8192 초과를 거부하고 PORT가 공개 web의 포트와 같은지 확인합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| plan_intent_mismatch / plan_workload_mismatch | BLOCK | commit·앱·서비스 관계 불일치 | 같은 분석으로 설계를 다시 생성합니다. |
| plan_state_mismatch | BLOCK | DB/저장 존재·경로 불일치 | 분석과 실제 저장 요구를 대조합니다. |
| plan_secret_mismatch / plan_config_mismatch | BLOCK | 설정·비밀 이름 관계 불일치 | 필요 이름과 값만 정확히 전달합니다. |
| plan_resource_unsupported | UNSUPPORTED | 예약 이름 또는 자원 상한 밖 | 지원 자원 범위를 검토합니다. |
| config_overrides_secret / config_policy_violation / config_not_supported | BLOCK 또는 UNSUPPORTED | 공통 설정 검사 | I-006의 이름·값별 조치를 적용합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

services·public_services를 기록합니다. 다른 관계의 기대값과 관찰값을 모두 저장하지는 않으므로 당시 Intent·Plan 자료를 함께 확인해야 합니다.

## 해결과 재검증 {#remedy}

1. 같은 commit의 Intent와 Plan을 항목별 비교합니다.
2. 분석 오류면 먼저 분석을 수정하고, 설계 오류면 Planner를 수정합니다.
3. 새 Plan의 형식·관계·대상 프로필을 재검사합니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 분석의 web·DB·저장을 대상에 맞게 전달 | PASS |
| 위반 | 형식은 맞지만 비밀 이름 NEW_SECRET 추가 | BLOCK |
| 경계 | 자원 상한 이내 | L-002 통과 가능; AWS 프로필은 256/512 요구 |
| 미지원 | CPU 4096 초과 | UNSUPPORTED |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.
