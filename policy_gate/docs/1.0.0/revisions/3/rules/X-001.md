# X-001 · 빌드 입력 프로필

정책 1.0.0 · 규칙 revision 1 · 문서 revision 3

## 목적 {#purpose}

최종 빌드 입력이 검토된 의존성·Prisma 생성기 조합인지 확인합니다.

## 입력과 적용 조건 {#inputs}

validate_patch가 반환한 메모리상의 파일 집합과 호스트 trusted-profile. 빌드 전이며 정책 업데이트 재검사에서도 사용합니다.

## 처리 과정 {#procedure}

1. package.json·lock·Prisma 스키마·src/server.js 존재를 요구합니다.
2. package JSON을 읽고 lock 해시 및 dependencies/devDependencies를 trusted-profile과 비교합니다.
3. generator가 정확히 하나이고 prisma-client-js provider만 설정되어 있는지 확인합니다.
4. provider 순서가 prisma-client-js, postgresql인지 검사하고 output/engineType/binaryTargets 설정을 거부합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| build_profile_incomplete / package_invalid | BLOCK | 필수 파일 없음 또는 JSON 오류 | 올바른 승인 변환 결과를 확보합니다. |
| unreviewed_dependency_lock / unreviewed_dependencies | BLOCK | lock·의존성 값이 승인 기준과 다름 | 패치 생성과 승인 템플릿의 버전을 확인합니다. |
| unsupported_prisma_generators / unsupported_prisma_output | UNSUPPORTED | 생성기·출력 설정 미지원 | 지원 설정을 확인하고 추가 기능은 별도 검토합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

file_count와 lock의 input_digest를 기록합니다. 이미지 취약점 검사 결과나 실제 빌드 성공은 아닙니다.

## 해결과 재검증 {#remedy}

1. 검증된 패치와 실제 Builder 입력의 연결을 먼저 확인합니다.
2. 승인 의존성·생성기 계약에 맞는 결과를 다시 생성합니다.
3. X-001 통과 뒤 Docker 빌드·이미지 식별·실행·접속 결과를 별도로 확인합니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 승인 lock·의존성과 PostgreSQL 생성기 | PASS |
| 위반 | 파일 누락 또는 lock 해시 변경 | BLOCK |
| 경계 | 패치 규칙 통과지만 다른 lock | X-001 BLOCK |
| 미지원 | 추가 generator 또는 사용자 출력 경로 | UNSUPPORTED |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.

## 한계와 관련 검사 {#limits}

일반 패키지 안전성 검증이 아닙니다. 정규식 기반 Prisma 빌드 설정 확인이어서 전체 언어 의미를 증명하지 않습니다. build 내부의 패치 재검사와 이미지 provenance 검증을 대체하지 않습니다.
