# I-000 · 분석 형식과 소스 식별

정책 1.0.0 · 규칙 revision 1 · 문서 revision 3

## 목적 {#purpose}

분석 형식·소스 식별·미해결 요구를 먼저 확인하여 잘못된 입력 위에서 세부 검사를 진행하지 않습니다.

## 입력과 적용 조건 {#inputs}

Intent와 호스트가 전달한 source_revision, source snapshot. Intent 단계의 첫 규칙입니다.

## Intent 필드 계약 {#contract}

Analyzer가 소스와 RepoMap을 읽어 Intent를 생성하며 Policy Gate는 이를 검증합니다. 호스트가 별도로 전달하는 snapshot은 읽을 소스 경로이고 source_revision은 비교 기준 commit입니다. snapshot 경로는 Intent 필드가 아닙니다. 다음 계약은 형식 조건이며 G-002의 검토된 앱 조건도 별도로 만족해야 합니다.

| 필드 | 필수·기본값 | 현재 허용 조건 |
|---|---|---|
| schema_version | 생략 시 1.0.0 | 문자열 1.0.0만 허용 |
| source_revision | 필수 | 소문자 16진수 40자리 Git SHA; 호스트 기준과 같아야 함 |
| app | 필수 | 소문자로 시작하고 소문자·숫자·하이픈, 1~41자 |
| runtime | 필수 | node22 |
| workloads | 필수, 최소 1개 | 이름 중복 금지, 공개 HTTP 정확히 1개 |
| state | 기본 빈 목록 | relational_db 또는 persistent_files |
| secrets | 기본 빈 목록 | 비밀정보의 이름만 전달; 대문자·숫자·밑줄, 대문자로 시작 |
| config | 기본 빈 객체 | 같은 이름 형식의 키와 문자열 값; 실제 허용 설정은 I-006 검사 |
| unknowns | 기본 빈 목록 | 형식상 문자열 목록이나 하나라도 있으면 I-000에서 unresolved_intent 차단 |

모든 계약 객체는 정의하지 않은 필드를 거부합니다. 선택 필드의 생략과 null은 같지 않습니다. 예를 들어 state 생략은 빈 목록이지만 null은 허용되지 않습니다. Pydantic의 기본 형 변환이 있으므로 모든 잘못된 JSON 타입을 엄격하게 거부한다고 해석하지 않습니다.

## 서비스와 상태의 조건 {#entities}

| 객체 | 반드시 들어갈 내용 | 조건·제한 |
|---|---|---|
| 공통 workload | name·kind·evidence | evidence 최소 1개; public 기본 false |
| HTTP | port·health | port 1~65535, health는 /로 시작, command는 null 또는 생략 |
| worker | command | public=false, port·health는 null 또는 생략; 명령과 근거는 I-002에서 추가 검사 |
| relational_db | engine·orm·evidence | sqlite 또는 postgresql, orm=prisma; path·reason은 null 또는 생략 |
| persistent_files | path·reason·evidence | 안전한 상대 경로와 비어 있지 않은 이유; engine·orm은 null 또는 생략 |

근거는 `src/server.js:22`처럼 저장소 상대 경로와 1부터 시작하는 줄 번호입니다. `../`, 절대 경로, 잘못된 구분자는 형식에서 거부합니다. 파일과 줄의 실제 존재는 I-001에서 확인합니다. I-003/I-004/I-002는 근거와 요구의 관계를 추가 검사합니다. reason에 문장이 있다는 사실 자체가 저장 필요성을 증명하지 않습니다.

## 검증된 입력 예시 {#example}

다음은 저장된 v1 fixture의 전체 Intent입니다. source_revision과 줄 번호는 이 fixture의 snapshot에 대응하므로 다른 앱에 그대로 복사할 값이 아닙니다. 실제 비밀값은 포함하지 않습니다. 문서 테스트는 아래 JSON 자체를 파싱하고 G-002와 Intent 검사를 실행합니다.

```json
{
  "schema_version": "1.0.0",
  "source_revision": "ebad709867cf1f3523075d8038ae41bd69ecae9b",
  "app": "demo-app",
  "runtime": "node22",
  "workloads": [
    {
      "name": "web",
      "kind": "http",
      "port": 3000,
      "public": true,
      "health": "/health",
      "command": null,
      "evidence": [
        "src/server.js:22",
        "src/server.js:87"
      ]
    }
  ],
  "state": [
    {
      "kind": "relational_db",
      "engine": "sqlite",
      "orm": "prisma",
      "path": null,
      "reason": null,
      "evidence": [
        "prisma/schema.prisma:6"
      ]
    },
    {
      "kind": "persistent_files",
      "engine": null,
      "orm": null,
      "path": "uploads/",
      "reason": "업로드한 사진이 재시작 후에도 남아야 함",
      "evidence": [
        "src/images.js:10",
        "src/images.js:23"
      ]
    }
  ],
  "secrets": [
    "DATABASE_URL"
  ],
  "config": {},
  "unknowns": []
}
```

출력은 검사된 Intent이며 새 요구를 만들어 넣지 않습니다. [SQLite에서 PostgreSQL까지의 검사 시점](../flow.md#checkpoints)과 [DB 실패 해결 사례](../cases.md#db-walkthrough)를 함께 읽으세요.

## 처리 과정 {#procedure}

1. 호스트 revision 형식을 확인하고 Intent 스키마를 파싱합니다.
2. Intent.source_revision과 호스트 revision을 비교하고 unknowns가 비었는지 확인합니다.
3. 심볼릭 링크를 따라가지 않고 소스를 읽습니다. 제외 경로, 파일 형식·크기·개수·UTF-8 제한을 적용합니다.
4. 읽은 파일 집합의 digest와 commit을 검사 실행에 연결합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| revision_invalid / revision_mismatch | BLOCK | 형식 오류 또는 commit 불일치 | 동일 commit의 분석·소스를 다시 확보합니다. |
| schema_invalid / unresolved_intent | BLOCK | 계약 밖 입력 또는 미해결 요구 | 형식·누락을 확인하고 분석을 완료합니다. |
| unreadable_source | BLOCK | 파일 열기 또는 UTF-8 처리 실패 | 소스 수집·권한·인코딩을 확인합니다. 현재 분류는 BLOCK이며 환경 오류와의 분리는 보완 과제입니다. |
| invalid_path / symlink_forbidden / non_regular_file / source_limit | BLOCK | 안전한 읽기 경계 위반 | 자료 구조·크기를 확인합니다. 링크를 따라 읽도록 우회하지 않습니다. |
| binary_source_unsupported | UNSUPPORTED | NUL 포함 소스 | 바이너리 실행 입력은 지원 범위 검토로 분리합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

성공한 읽기 이후 source_revision·file_count·input_digest가 남습니다. 읽기 이전 실패라면 관찰값이 비어 있을 수 있습니다.

## 해결과 재검증 {#remedy}

1. 실패 코드로 분석 데이터 문제와 소스 읽기 문제를 구분합니다.
2. 소스/분석을 같은 commit으로 확보하거나 검사 환경을 복구합니다.
3. I-000부터 재실행합니다. 후속 규칙 NOT_RUN을 별도 위반으로 세지 않습니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 동일 revision·unknowns 없음·읽을 수 있는 소스 | PASS |
| 위반 | 다른 revision 또는 unknowns 존재 | BLOCK |
| 경계 | 2000개 초과 또는 크기 초과 | BLOCK · source_limit |
| 오류 | 알 수 없는 예외 | ERROR · policy_check_failed; 원문 비밀값 출력 안 함 |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.

## 한계와 관련 검사 {#limits}

파일 최대 4MiB, 총 20MiB, 파일 2000개 제한입니다. 디렉터리·비밀 경로 제외로 파일이 빠질 수 있습니다. source_revision이 올바르다는 것은 원격 Git 서명 검증을 의미하지 않습니다.
