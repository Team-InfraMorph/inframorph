# G-003 · 지원 배포 프로필

정책 1.0.0 · 규칙 revision 1 · 문서 revision 3

## 목적 {#purpose}

B가 만든 설계가 승인된 Local/AWS 실행 프로필을 벗어나지 않게 합니다.

## 입력과 적용 조건 {#inputs}

Plan, RepoMap 및 호스트가 지정한 local/aws 대상. Plan 스키마 파싱 뒤 실제 서비스·저장·설정 값을 대조합니다.

## 처리 과정 {#procedure}

1. web 3000 /health 공개, 필요하면 worker 비공개라는 기대 서비스를 구성합니다.
2. commit·앱·대상·서비스 목록과 DB/저장 존재, uploads 경로, DATABASE_URL 이름을 비교합니다.
3. Local은 STORAGE_DRIVER=fs, AWS는 s3와 서비스별 CPU 256·메모리 512를 요구합니다. PORT 생략은 3000으로 간주합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| plan_source_mismatch | BLOCK | 지원 대상·서비스·저장·설정·AWS 자원 값 불일치 | 분석과 대상 환경을 확인하여 설계를 다시 생성합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

source_revision·target·services·public_services를 기록합니다. 실제 클라우드 보안 그룹 관측값은 없습니다.

## 해결과 재검증 {#remedy}

1. Plan이 어떤 대상의 어떤 commit인지 확인합니다.
2. 잘못된 설계를 수정하고 G-003 및 L-001/L-002를 다시 검사합니다.
3. UI에서 문서 버전을 선택하는 것은 실행 프로필 변경 방법이 아닙니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | Local fs 또는 AWS s3의 검토 설계 | PASS |
| 위반 | NODE_OPTIONS 등 실행 설정 삽입 | BLOCK |
| 경계 | PORT 생략 | 다른 조건이 같으면 3000으로 비교 |
| 오류 | 잘못된 Plan 스키마 | 이 진입점의 모델 파싱 예외는 ERROR 가능; L-001의 schema_invalid와 구분 |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.
