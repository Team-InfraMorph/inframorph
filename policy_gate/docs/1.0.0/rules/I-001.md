# I-001 · 근거 파일과 줄

정책 1.0.0

## 목적 {#purpose}

AI가 실제 소스에 없는 파일·줄을 인용한 분석을 다음 단계로 넘기지 않습니다. 인용 내용의 의미를 증명하는 규칙은 아닙니다.

## 입력과 적용 조건 {#inputs}

I-000에서 읽은 소스 파일 집합과 Intent의 workloads·state에 포함된 evidence 목록을 사용합니다. 경로와 양수 줄 번호의 형식은 앞선 스키마 검사가 처리합니다.

## 처리 과정 {#procedure}

1. 각 workload와 state의 모든 인용을 경로와 줄 번호로 분리합니다.
2. 해당 경로가 필터링된 소스 집합에 있는지 검사합니다. .env 등 제외 파일은 디스크에 있어도 근거 파일로 인정하지 않습니다.
3. UTF-8 내용을 줄로 나누어 인용 줄이 전체 줄 수 이하인지 검사합니다. 첫 실패에서 종료하므로 뒤의 인용과 I-006 이후 규칙은 검사하지 않을 수 있습니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| evidence_file_missing | BLOCK | 파일이 수집된 소스 집합에 없음 | 당시 commit·수집 경로·제외 목록을 확인하고 실제 근거를 찾아 분석을 다시 생성합니다. |
| evidence_line_missing | BLOCK | 파일은 있지만 인용 줄이 범위 밖 | 현재 파일에서 근거 줄을 다시 찾습니다. 없는 줄을 맞추려고 빈 줄을 추가하지 않습니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

검사한 인용 목록 references를 남깁니다. 개별 오류의 path·line은 이 함수에서 별도로 설정하지 않으므로 결과에 없을 수 있습니다. 목록만 보고 어떤 인용이 실패했는지 임의로 확정하지 않습니다.

## 해결과 재검증 {#remedy}

1. 당시 source_revision과 현재 보고 있는 파일이 같은지 확인합니다.
2. 해당 인용이 실제 주장과 관련 있는지 확인한 뒤 분석 결과를 수정하거나 다시 생성합니다.
3. 실제 배포는 소스 프로필부터 재검사합니다. I-001의 새 통과뿐 아니라 뒤의 DB·저장·worker 검사도 완료됐는지 확인합니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

실패 입력부터 해결 결과까지는 [수정·재검증 사례](../cases.md#evidence-walkthrough)를 확인하세요.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 존재하는 src/server.js의 유효한 줄 | I-001 PASS |
| 위반 | 없는 파일 또는 마지막 줄보다 큰 줄 | BLOCK · 위 사유 코드 |
| 경계 | 존재하는 빈 줄 | I-001 단독 PASS 가능; G-002는 거부 |
| 오류 | 파일을 읽을 수 없음 | 이 규칙 전 I-000에서 처리; I-001 NOT_RUN |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.

## 한계와 관련 검사 {#limits}

빈 줄도 I-001의 존재 조건은 통과할 수 있습니다. demo 배포의 G-002는 빈 근거 줄을 먼저 거부합니다. 파일·줄이 존재해도 DB·저장 의미는 I-003/I-004 등이 별도로 검사합니다.
