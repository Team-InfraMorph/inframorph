# I-004 · 파일 저장 근거

정책 1.0.0

## 목적 {#purpose}

선언된 파일 저장 요구가 검토된 실제 읽기·쓰기 코드에 연결되는지 확인합니다.

## 입력과 적용 조건 {#inputs}

Intent.state의 persistent_files 항목과 src/images.js, 인용 줄. 저장 요구가 없으면 적용 제외합니다.

## 처리 과정 {#procedure}

1. 저장 경로의 끝 /를 제거하여 uploads인지 확인합니다.
2. src/images.js가 존재하고 검토된 BASE_IMAGES 해시와 같은지 확인합니다.
3. JS 파서의 호출 목록에서 readFile/writeFile 위치를 얻습니다.
4. 각 저장 항목의 근거 중 하나 이상이 이 호출 범위와 겹쳐야 합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| storage_path_unsupported / storage_evidence_unsupported | UNSUPPORTED | 경로나 코드 형태가 검토 범위 밖 | 지원 범위를 확인하고 저장 구현을 별도 검토합니다. |
| storage_evidence_unrelated | BLOCK | 인용이 지원 읽기/쓰기 호출과 무관 | 실제 저장 동작을 가리키는 근거를 찾습니다. |
| javascript_parser_unavailable | ERROR | 파서 실행 실패 | 검사 환경을 복구한 뒤 같은 입력을 재검사합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

references를 기록합니다. 선택된 호출 노드 전체나 실제 파일 쓰기 결과는 기록하지 않습니다.

## 해결과 재검증 {#remedy}

1. 저장 요구의 경로와 해당 소스의 실제 동작을 확인합니다.
2. 근거 오류와 지원 밖 구현을 구분하여 수정 또는 지원 검토합니다.
3. 새 분석부터 검사합니다. 저장 요구를 지워 적용 제외시키는 것은 해결 방법이 아닙니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 검토된 코드의 readFile 또는 writeFile 인용 | PASS |
| 위반 | 무관한 src/server.js 인용 | BLOCK |
| 경계 | persistent_files 항목 없음 | I-004 NOT_APPLICABLE; 실제 G-002는 누락 차단 |
| 오류 | JS 파서 장애 | ERROR |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.

## 한계와 관련 검사 {#limits}

읽기와 쓰기 양쪽을 각각 인용하도록 강제하지 않고 지원 호출 중 하나와의 연결을 봅니다. 저장 요구 누락 자체는 I-004에서 찾지 않지만 실제 demo 배포의 G-002는 저장 요구 존재를 강제합니다.
