# 정책 책임과 경계

## 제품의 실패와 현재 방어 {#boundaries}

| 막으려는 실패 | 현재 담당 검사와 연결 | 남는 한계 |
|---|---|---|
| 오래된 분석·다른 소스로 빌드 | G-002·I-000·L-002·P-001, snapshot/bundle fingerprint와 이미지 provenance | 원격 Git 서명 검증은 아님 |
| AI가 DB·저장·worker를 누락 | G-002의 고정 demo 요구, I-003의 스키마 DB, I-002의 scripts.worker | I-004 자체는 저장 요구가 있을 때만 수행; 범용 발견 기능 부족 |
| 분석과 다른 자원·공개 범위 | G-003·L-001·L-002 | 실제 클라우드 노출 관측은 별도 |
| 패치에 무관한 앱 기능 포함 | P-001 경로, P-006 AST, P-003 구조, P-004 허용 변환, P-005 의존성 | 업무 의미와 모든 동작 동등성 증명 아님 |
| 검사 후 내용 바꿔 실행 | P-002 적용 결과, 빌드 직전 패치 재검사, 검증 바이트로 빌드, 이미지 식별 확인 | 현재 서비스의 지속적 drift 감시 아님 |
| 일부만 검사했는데 전체 통과 | 규칙 실행 ledger, 필수 규칙 대조, 저장 실패 시 실행 중단 | 과거 legacy 요약은 규칙별로 복원 불가 |
| 토큰·실행 능력 포함 | P-007 패턴·P-006 정적 AST·소스 프로필 | 일반 비밀정보 탐지나 악성코드 탐지율 보장 없음 |

## 방어는 전체 경로로 판단합니다 {#layered}

I-004는 persistent_files 분석이 없으면 적용 제외됩니다. 이것만 보고 “저장 기능을 숨기면 배포 가능”이라고 결론내리면 안 됩니다. 실제 demo 경로의 G-002가 DB와 파일 저장 상태를 정확히 요구하여 누락을 먼저 차단합니다. 반대로 이 경계가 사라질 미래 범용 앱 지원에서는 누락 탐지가 새 과제입니다.

P-006이 모든 JS 위험을 찾아내지는 않지만 G-002는 원본 실행 파일을 제한하고 P-004는 승인된 AST 변환만 허용합니다. 개별 탐지 한계와 현재 지원 경로에서 가능한 우회를 분리합니다.

## 역할과 책임 {#ownership}

개발자는 원본 앱·분석·패치의 사실을 확인합니다. 운영자는 당시 대상·입력·검사 환경·재검증 결과를 확인합니다. 정책 담당자는 지원 범위·판정 조건·검증 사례 변경을 검토합니다. 운영자의 확인은 BLOCK/ERROR 면제가 아닙니다.
