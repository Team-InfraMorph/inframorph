# 정책 변경 이력

## 1.1.0 {#policy-baseline}

검토된 demo-app Node 22 입력에 대한 정책 관리 기준입니다. 출시 태그·릴리스 기록을 자동으로 생성하지 않습니다.

| 영역 | 포함된 내용 | 확인할 설명 |
|---|---|---|
| 검사 | 지원 소스·Intent·설계·패치·빌드 입력의 18개 규칙, 실제 결과와 미실행 구분 | [규칙별 설명](rules/I-000.md#purpose) |
| 입력 계약 | Intent·Plan·manifest의 필수값·조건·실제 검증된 전체 예시 | [Plan 계약](rules/L-001.md#contract), [패치 계약](rules/P-001.md#contract) |
| 실패 처리 | 사유별 수정 안내, 실패→새 검사→원인 검토 연결 | [문제 해결](troubleshooting.md#reasons), [기록 예시](logs.md#walkthrough) |
| 배포 영향 | 보존 자료 재검사·검토·수동 재배포와 자료 부족의 구분 | [전환 안내](upgrade.md) |
| 문서 탐색 | 정책 버전별 목차·검색·고정 절·변경 이력 | [버전 관리](versioning.md#versions) |

## 설명과 관리 방식 정리 {#documentation}

문서도 정책 버전 1.1.0의 한 묶음으로 제공합니다. 문서 탐색 방식은 유지합니다. 이번 직접 근거 강화는 판정 조건도 바꾸므로 아래 변경과 적용 대상을 따로 기록합니다. 문서 선택과 링크는 정책 버전을 기준으로 하며 설명의 변경 차이는 Git에 남습니다.

과거 판정의 버전·입력·결과·문서 해시는 덮어쓰지 않습니다. 검사 결과에서 문서를 열면 해당 버전의 현재 설명이 열리고, 과거 설명의 정확한 내용은 저장된 해시와 Git 이력에서 확인합니다. 문서를 읽거나 버전을 선택하는 동작이 활성 정책을 변경하지는 않습니다.

## legacy 2.2.0 {#legacy}

관리 체계 도입 전 단계별 요약입니다. 정식 1.1.0의 이전 SemVer 릴리스가 아니며 새 규칙 결과로 재표기하지 않습니다. 존재하지 않는 과거 1.x 릴리스를 만들지 않습니다.

## 1.0.0에서의 변경 {#bounded-repair}

배포당 총 3회 이내에서 Intent·Plan·코드 패치의 교정 가능한 차단을 처리합니다. 원래 BLOCK과 각 수정 diff·사용량·재검사 결과를 보존합니다. 파일 변조·시크릿·금지 코드·미지원 소스·검사 환경 오류는 자동 승인하지 않습니다. 저장된 롤백 계획은 자동 수정하지 않습니다. 검증된 Local 패치는 AWS에서도 동일 소스로 다시 검사합니다. 이 버전은 개발 중이며 출시·원격 배포를 의미하지 않습니다.


## 직접 근거 강화 {#evidence-hardening}

| 규칙 | 이전 동작 | 새 동작 | 영향을 받는 사례 |
|---|---|---|---|
| I-003 · 정의 1 → 2 | datasource 범위와 인용이 겹치면 인정 | provider 키·값 토큰 줄 인용 필요 | DB 종류는 맞지만 URL·중괄호만 인용한 분석 |
| I-002 · 정의 1 → 2 | worker 파일의 비어 있지 않은 줄 또는 명령 줄 인정 | scripts.worker 명령 값과 검토된 시작 호출 모두 인용 | 초기화 코드만 또는 명령만 인용한 분석 |

기존 1.1.0의 자동 수정 기능은 유지하며, 새 근거 부족 사유에만 서버의 evidence 전용 수정 범위를 적용합니다. 수정 기준은 최초 Intent로 고정하고 범위 위반은 evidence_repair_scope_violation으로 종료합니다. 모델이 결론·명령·비밀정보·원본 소스를 바꿔 통과시키는 절차가 아닙니다.

새 배포는 강화 조건을 통과해야 합니다. 과거 배포의 원래 PASS는 보존하고 보존 자료 재검사의 BLOCK은 ‘근거 보완 권고 · 서비스 유지’로 안내합니다. worker 없는 소스에는 I-002 강화 권고를 붙이지 않습니다. 자료가 없으면 영향 없음이 아닌 확인 필요입니다. 정책 업데이트만으로 재배포가 필요하다고 판단하지 않습니다.

이 변경은 기존 통과 입력을 제한합니다. 개발 상태의 1.1.0에 통합한 계약 변경이며 일반 버전 원칙의 예외를 숨기지 않습니다. 1.0.0의 동작과 당시 기록을 덮어쓰지 않습니다. [버전 원칙](versioning.md#repair-identity)과 [필요한 조치](upgrade.md#evidence-hardening)를 확인하세요.
