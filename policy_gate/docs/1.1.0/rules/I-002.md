# I-002 · worker 실행 근거

정책 1.1.0 · 규칙 정의 2

## 목적 {#purpose}

worker 파일이 존재한다는 사실과 worker가 시작되도록 구성됐다는 사실을 구분합니다. **등록된 실행 명령 → 그 명령의 진입 파일 → 검토된 시작 호출**을 연결해야 분석을 다시 확인할 수 있습니다. 정적 시작 근거이며 실제 worker 실행 성공을 판정하지 않습니다.

## 입력과 적용 조건 {#inputs}

Intent.workloads의 worker 항목·명령·evidence, 원본 package.json의 scripts.worker와 진입 JS 파일을 사용합니다. 앞선 근거·DB·저장 검사를 통과한 뒤 실행합니다. worker가 없는 V1에는 시작 인용을 요구하지 않지만, scripts.worker가 있는데 분석에서 빠진 경우는 계속 검사합니다.

## 처리 과정 {#procedure}

1. 명령을 실행하지 않고 분리해 `node src/...js`의 지원 형태와 안전한 경로인지 확인합니다. 진입 파일이 없으면 중단합니다.
2. JavaScript 구문 분석기로 진입 파일을 읽습니다. 현재 검토된 형태는 최상위에 정의된 tick과 연결되는 최상위 `setInterval(tick, …)` 또는 `tick()`입니다. 재할당·가려진 이름·문자열·주석·호출되지 않는 함수 내부 코드는 시작점으로 인정하지 않습니다.
3. JSON 파서로 scripts.worker 경로의 실제 값 토큰 위치를 찾고 Intent 명령과 정확히 같은지 비교합니다. 다른 script나 description의 같은 문자열은 명령 근거가 아닙니다.
4. 기존의 명령·진입 파일 관련성 검사를 유지한 뒤, 해당 worker evidence가 **명령 값 토큰 줄과 시작 호출 토큰 줄을 모두** 포함하는지 확인합니다. setInterval 호출에서는 callee 또는 tick 콜백 토큰 줄, 직접 호출에서는 tick 토큰 줄을 인용할 수 있습니다.
5. 등록된 scripts.worker가 분석에서 누락되지 않았는지 확인합니다. 명령 근거가 먼저 부족하면 그 사유로 종료하지만 진단에는 시작 근거의 부족도 함께 남습니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| worker_command_unsupported | UNSUPPORTED | 지원 Node 명령 형태 밖 | 임의 셸을 추가하지 말고 지원 명령 계약을 확인합니다. |
| worker_entry_missing | BLOCK | 명령의 진입 파일 없음 | 같은 소스의 실제 경로와 분석을 확인합니다. |
| worker_evidence_unrelated | BLOCK | 기존 명령·진입 파일 관련성조차 없음 | 실제 명령과 시작 코드를 찾습니다. |
| worker_command_evidence_missing | BLOCK | scripts.worker의 정확한 명령 값 줄 인용 부족 | package.json에서 필요한 명령 위치를 확인하고 해당 evidence에 추가합니다. |
| worker_start_evidence_missing | BLOCK | 검토된 시작 호출 줄 인용 부족 | 기록된 시작 후보 위치를 확인하고 같은 항목의 evidence에 추가합니다. |
| worker_requirement_missing | BLOCK | 등록된 worker 명령이 분석에서 누락 | 정상 분석 경로에서 worker 요구를 보완합니다. |
| package_invalid | BLOCK | package JSON 형식·중복 키 등 모호한 선언 | 원본 파일의 형식과 지원 프로필을 확인합니다. |
| javascript_syntax_invalid | BLOCK | 진입 JS 구문 분석 실패 | 소스 문법과 검토된 원본 여부를 확인합니다. 근거 추가로 면제할 수 없습니다. |
| javascript_parser_unavailable | ERROR | JS 검사기를 실행할 수 없음 | 검사 환경을 복구하고 같은 입력을 재검사합니다. 앱 위반과 구분합니다. |

공통 JS 검사기 장애는 앞선 저장 코드 검사 I-004에서 먼저 발생할 수도 있습니다. 실제 기록의 rule_id와 실행 순서를 확인하며 위 코드를 항상 I-002의 첫 실패라고 해석하지 않습니다.

I-002 PASS는 명령과 시작 코드의 정적 연결을 확인했다는 뜻입니다. 앞선 I-003 등이 실패하면 I-002는 NOT_RUN으로 남으며 시작 검사를 수행한 것으로 표시하지 않습니다.

## 근거 읽기 {#evidence}

분석 명령, 소스에서 확인한 등록 명령, 지원 시작점 수, 제출 인용, 명령·시작점의 필요한 파일·줄과 부족한 역할을 확인합니다. 역할은 worker_command와 worker_start입니다. UI의 ‘인용 확인’은 실제 프로세스 실행이나 메모 집계 이벤트 관찰을 뜻하지 않습니다. 과거 결과에 이 필드가 없으면 미보존으로 안내합니다.

## 해결과 재검증 {#remedy}

1. 당시 source_revision과 명령·진입 파일을 맞춰 봅니다.
2. 명령은 맞고 초기화만 인용했다면 scripts.worker의 값 줄과 최상위 시작 호출 줄을 해당 worker evidence에 넣습니다. DB·다른 workload·명령 자체를 함께 바꾸지 않습니다.
3. 새 배포의 AI는 해당 evidence만 제안합니다. 최초 Intent와 비교해 범위를 강제하고 G-002와 전체 Intent 규칙을 다시 실행합니다. 3회 제한 안에서 해결하지 못하면 후속 Planner·Builder로 진행하지 않습니다.
4. 원본에 지원 시작점이 없다면 인용을 꾸미지 않습니다. 현재 지원 범위와 앱 변경 필요성을 검토합니다. 과거 보존 자료는 자동 수정하지 않으며 후속 정상 배포와 연결합니다.

## 검증 사례 {#cases}

| 상황 | 인용 | 결과 |
|---|---|---|
| 지원 worker | 명령 값 + 최상위 setInterval 또는 tick 호출 | PASS |
| 초기화 코드만 인용 | dotenv 초기화 줄 | 명령 근거 부족; 진단에는 두 역할 모두 부족 |
| 명령만 인용 | package scripts.worker 값 줄 | 시작 근거 부족 |
| 시작점만 인용 | 최상위 tick 호출 줄 | 명령 근거 부족 |
| 초기화 + 명령 | 두 파일에 인용은 존재하지만 시작점 없음 | 시작 근거 부족 |
| 호출 문자열·미호출 함수 내부 | 텍스트나 중첩된 tick 호출 | 시작점으로 인정하지 않음 |
| worker 없는 V1 | worker도 scripts.worker도 없음 | PASS; 시작 인용 요구 없음 |

지원 원본의 인용만 바꾼 사례는 G-002부터 실행합니다. 가짜 시작점·가려진 함수·여러 줄 예시는 파서 단위 검증이며 미검토 소스를 지원한다는 뜻이 아닙니다.

## 한계와 관련 검사 {#limits}

임의 worker 프레임워크·큐·스케줄러를 발견하는 규칙이 아닙니다. 현재 scripts.worker와 검토된 tick 시작 형태만 다룹니다. 함수가 실제로 성공하는지, 영구 실행하는지, 외부 서비스에 연결되는지, 집계값이 맞는지는 배포 실행 검증의 책임입니다. 같은 이름이 있다는 사실만으로 일반 코드의 의미를 증명하지 않습니다.

## 변경 이력 {#history}

이전에는 진입 파일의 비어 있지 않은 줄 또는 package의 명령 줄 중 하나를 인정했습니다. 1.1.0 규칙 정의 2는 등록 명령과 정적으로 연결된 시작점의 인용을 모두 요구합니다. 기존 통과 입력 일부를 제한하는 판정 변경이며, 개발 상태의 1.1.0에 통합했습니다. 1.0.0 문서·당시 기록은 보존합니다.
