# I-003 · DB 종류와 근거 일치

정책 1.1.0 · 규칙 정의 2

## 목적 {#purpose}

DB 종류가 맞다는 결론과 그 결론을 설명하는 근거를 함께 확인합니다. AI가 sqlite라고 맞게 분석했더라도 URL 설정이나 닫는 중괄호만 인용하면 다른 사람이 DB 종류를 확인할 수 없습니다. 이 규칙은 **분석의 DB 종류를 실제 datasource의 provider 선언에 직접 연결**합니다.

## 입력과 적용 조건 {#inputs}

고정된 소스의 `prisma/schema.prisma`, Intent의 relational_db 항목과 evidence를 사용합니다. 실행 순서는 지원 소스 G-002 → 입력 I-000 → 인용 실존 I-001 → 설정 I-006 → I-003입니다. 선행 검사가 실패하면 I-003은 실행하지 않습니다.

스키마와 DB 주장이 모두 없으면 PASS이며 DB 존재를 새로 증명한 것은 아닙니다. 현재 지원 소스에서 요구사항 자체가 틀리면 G-002가 먼저 차단할 수 있습니다.

## 처리 과정 {#procedure}

1. 주석과 공백을 제외하는 Prisma 토큰 파서로 지원되는 단일 datasource와 provider를 읽습니다. generator의 provider는 DB 선언으로 사용하지 않습니다.
2. 스키마가 있는데 DB 요구가 빠졌는지, 각 DB 항목의 engine이 관찰한 sqlite 또는 postgresql과 같은지 확인합니다.
3. 기존의 datasource 범위 관련성 검사를 유지합니다. 전혀 다른 파일·영역의 인용은 `db_evidence_unrelated`로 차단합니다.
4. 파서가 확인한 datasource의 **provider 키 토큰 또는 값 토큰이 있는 줄** 중 하나 이상을 해당 DB 항목이 인용했는지 확인합니다. 같은 블록의 URL·중괄호·주석만 인용하면 `db_provider_evidence_missing`입니다.
5. provider 선언이 여러 줄이면 키 줄 또는 값 줄은 인정하지만, 사이의 공백·주석·등호만 있는 줄은 인정하지 않습니다. 고정 줄 번호나 단순 문자열 검색으로 판단하지 않습니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| db_requirement_missing | BLOCK | 스키마는 있으나 DB 요구가 없음 | 실제 DB 요구와 분석 누락을 대조하고 정상 분석 경로에서 보완합니다. |
| db_provider_mismatch | BLOCK | 분석 engine과 datasource provider가 다름 | 같은 소스의 선언을 확인합니다. 분석 오류를 수정하며, 실제 DB 변경이라면 앱 변경과 마이그레이션 검토가 필요합니다. |
| db_evidence_unrelated | BLOCK | datasource와 관계없는 인용 | 해당 스키마의 provider 선언을 확인합니다. |
| db_provider_evidence_missing | BLOCK | datasource에는 걸치지만 provider 키·값 줄을 인용하지 않음 | 기록의 필요한 선언 위치를 확인하고 해당 DB 항목의 evidence만 보완합니다. |
| db_schema_missing | BLOCK | DB를 주장하지만 지원 경로 스키마 없음 | 경로·ORM의 지원 범위를 확인합니다. 통과용 파일을 만들지 않습니다. |
| prisma_structure_unsupported | UNSUPPORTED | 제한된 Prisma 파서가 지원하지 않는 구조 | 지원 확대 검토 대상으로 남깁니다. 인용만 바꿔 해결할 수 없습니다. |

조건을 만족하면 I-003 PASS입니다. 뒤의 저장·worker·설계·패치 검사는 별도로 수행합니다. 공통 입력 읽기 오류나 선행 실패는 [결과 분류](../results.md#classification)의 실제 실행 위치를 확인합니다. Prisma 파서는 외부 모델을 호출하지 않습니다.

## 근거 읽기 {#evidence}

결과에는 분석 engine, 관찰 provider, 제출한 인용, 필요한 provider 토큰 줄, 부족한 역할 `db_provider`와 허용된 evidence 위치가 남습니다. 같은 소스 snapshot 기준의 위치이며 다른 commit의 줄 번호와 섞지 않습니다. 접속 문자열과 비밀값은 저장하지 않습니다.

파싱 전에 실패했거나 과거 기록이면 이 정보가 없을 수 있습니다. 세부 정보의 부재를 잘못된 DB 설정의 증거로 해석하지 않습니다.

## 해결과 재검증 {#remedy}

1. 당시 정책 식별값·source_revision·소스와 분석 DB 항목을 확인합니다.
2. DB 종류는 같고 직접 근거만 부족하면 필요한 provider 줄을 인용합니다. 새 배포의 AI 보완도 이 항목의 evidence만 바꿀 수 있습니다. engine·reason·다른 항목 변경은 허용하지 않습니다.
3. 호스트가 G-002와 전체 Intent 검사를 다시 수행합니다. I-003만 통과하고 worker 등 다른 필수 검사가 실패하면 Planner로 진행하지 않습니다.
4. 과거 배포는 보존 입력을 그대로 재검사합니다. 당시 PASS는 유지하고 현재 BLOCK을 ‘근거 보완 권고 · 서비스 유지’로 별도 안내합니다. 수정한 분석은 후속 정상 배포의 새 검사로 확인합니다.

## 검증 사례 {#cases}

| 상황 | 제출 근거 | 결과와 다음 단계 |
|---|---|---|
| DB 종류와 직접 선언이 일치 | datasource provider 키 또는 값 줄 | PASS; 다음 Intent 규칙 실행 |
| DB 종류는 맞지만 URL만 인용 | 같은 datasource의 URL 줄 | db_provider_evidence_missing; 이후 규칙 미실행 |
| 닫는 중괄호만 인용 | datasource 마지막 줄 | 같은 부족 사유; engine을 변경할 이유가 아님 |
| generator provider만 인용 | 다른 블록의 provider 줄 | 기존 db_evidence_unrelated; DB 선언으로 사용하지 않음 |
| 여러 줄 선언 | provider 키 줄 또는 문자열 값 줄 | 인용 가능한 직접 토큰 위치로 인정 |
| 주석·등호 줄만 인용 | provider 사이의 비선언 토큰 줄 | 직접 근거로 인정하지 않음 |

URL·중괄호 사례는 검토된 원본 바이트를 유지하고 G-002부터 실제 순서로 재현합니다. 여러 줄·주석 사례는 파서 단위 검증이며 그런 변형 소스의 제품 지원을 의미하지 않습니다.

## 한계와 관련 검사 {#limits}

현재의 제한된 Prisma 구조에 대한 정적 검증입니다. 실제 DB 연결, 데이터 유지, 마이그레이션 성공을 보장하지 않습니다. G-002가 정확한 원본과 요구사항을 제한하므로 이 변경은 악성 앱 실행 우회를 발견했다는 의미가 아닙니다. 핵심은 올바른 결론도 직접 근거로 검토하고 제한된 범위에서 수정하는 것입니다.

## 변경 이력 {#history}

1.0.0과 강화 전 1.1.0은 datasource 블록과 인용이 겹치면 인정했습니다. 현재 1.1.0의 규칙 정의 2는 provider 키·값의 직접 인용을 추가로 요구합니다. 이전 PASS 일부가 새 기준에서 BLOCK이 되는 실제 계약 제한입니다. 개발 상태인 1.1.0에 통합했으며 호환 기능 추가나 문구 정정으로 분류하지 않습니다. [버전 관리](../versioning.md#repair-identity)에서 같은 버전의 서로 다른 정책 식별값도 확인하세요.
