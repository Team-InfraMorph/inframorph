# L-001 · 설계 형식

정책 1.0.0

## 목적 {#purpose}

실행 대상·서비스·저장 형태가 Plan 계약을 만족하는지 확인합니다. 이후 관계 검사의 안전한 입력을 만듭니다.

## 입력과 적용 조건 {#inputs}

Intent와 Plan 전체. validate_plan 진입에서 두 스키마를 파싱합니다. 다른 진입점의 사전 파싱에서 먼저 실패할 수도 있습니다.

## Plan 필드 계약 {#contract}

아래는 JSON 입력 계약입니다. 필수는 키가 있어야 한다는 뜻이고, 기본값은 **키를 생략했을 때** 적용됩니다. 객체의 미등록 필드는 거부합니다. null 허용과 키 생략은 다르며, 전체 모델은 엄격 타입 모드가 아니므로 일부 값은 Pydantic 기본 변환을 거칩니다. 아래 형식 그대로 보내는 것을 기준으로 합니다.

| 필드 | 필수·기본값 | 형식과 조건 |
|---|---|---|
| schema_version | 생략 시 "1.0.0" | 다른 버전은 거부 |
| source_revision | 필수 | 소문자 16진수 40자리 Git SHA. Intent·RepoMap과의 연결은 후속 관계 검사도 필요 |
| target | 필수 | local / aws / onprem. 스키마 허용이 해당 대상의 정책 재검사 지원을 보장하지 않음 |
| app | 필수 | 소문자로 시작하는 1~41자; 소문자·숫자·하이픈 |
| image_tag | 필수 | 정확히 app:<source_revision> |
| services | 필수 | 최소 1개. 이름 중복 금지, public=true인 HTTP 정확히 1개 |
| db | 생략 시 null | 아래 DB 객체. 있으면 secrets에 DATABASE_URL 이름 필요 |
| storage | 생략 시 null | 아래 저장소 객체. 있으면 대상에 맞는 STORAGE_DRIVER 필요 |
| secrets | 생략 시 [] | 대문자로 시작하는 환경변수 이름 목록. 비밀 값이 아님 |
| config | 생략 시 {} | 환경변수 이름 → 문자열 값. 비밀 이름 충돌 등은 L-002에서 별도 확인 |
| logs | 필수 | Local·onprem은 docker, AWS는 cloudwatch |
| est_monthly_krw | 생략 시 null | 0 이상 정수. 실제 요금 검증 결과가 아님 |
| mermaid | 필수 | 길이 1 이상 문자열. 스키마가 그림의 의미나 문법을 검증하지 않음 |

## 서비스·DB·저장소 계약 {#entities}

| 객체 | 필수값 | 생략값·추가 조건 |
|---|---|---|
| services 항목 | name, kind, cpu, mem | 이름 형식은 app과 같음. kind=http/worker. cpu·mem은 0보다 큰 정수이며 스키마에 자원 상한은 없음 |
| HTTP 서비스 | port, health | port=1~65535, health는 /로 시작. public 기본 false, command 기본 null. 스키마만으로 HTTP command를 금지하지 않으며 검토 프로필 G-003이 실행 구성을 더 제한 |
| worker 서비스 | command | 비어 있지 않은 문자열. public=false, port=null, health=null이어야 함. 명령 의미·허용 범위는 G-003·L-002에서도 확인 |
| db | type, patch | type=postgres_container 또는 rds_postgres, patch=sqlite_to_postgres |
| storage | type, patch, path | type=volume 또는 s3, patch=fs_to_storage. path는 저장소 상대 경로; 절대 경로·역슬래시·빈 구성요소·.·.. 금지 |

| 대상 | DB가 있으면 | 저장소가 있으면 | 로그 |
|---|---|---|---|
| Local | postgres_container | volume, STORAGE_DRIVER=fs | docker |
| AWS | rds_postgres | s3, STORAGE_DRIVER=s3 | cloudwatch |
| onprem | postgres_container | volume, STORAGE_DRIVER=fs | docker |

위 표는 모델 계약입니다. 현재 G-003의 Local/AWS 검토 프로필과 온프레미스의 Local 이미지 재사용·재검사 한계는 [실행 흐름](../flow.md#pipeline)에서 구분합니다. Plan 스키마 통과만으로 임의 앱·자원·명령을 실행할 수 없습니다.

## 검증된 Local Plan 전체 예시 {#example}

검토된 v1 소스와 [Intent 예시](I-000.md#example)를 입력으로 사용한 Local 설계입니다. 자동 검증에서 G-003·L-001·L-002가 통과합니다. DB·저장소가 필요 없는 앱의 최소 예시는 아니며 실제 배포 성공 기록도 아닙니다.

```json
{
  "schema_version": "1.0.0",
  "source_revision": "ebad709867cf1f3523075d8038ae41bd69ecae9b",
  "target": "local",
  "app": "demo-app",
  "image_tag": "app:ebad709867cf1f3523075d8038ae41bd69ecae9b",
  "services": [
    {
      "name": "web",
      "kind": "http",
      "cpu": 256,
      "mem": 512,
      "port": 3000,
      "health": "/health",
      "public": true,
      "command": null
    }
  ],
  "db": {
    "type": "postgres_container",
    "patch": "sqlite_to_postgres"
  },
  "storage": {
    "type": "volume",
    "patch": "fs_to_storage",
    "path": "uploads/"
  },
  "secrets": [
    "DATABASE_URL"
  ],
  "config": {
    "STORAGE_DRIVER": "fs"
  },
  "logs": "docker",
  "est_monthly_krw": 0,
  "mermaid": "flowchart LR\nweb --> db\nweb --> storage"
}
```

이 예시의 CPU·메모리·경로는 검토된 입력값입니다. 다른 값의 스키마 허용 여부와 실제 지원 프로필의 허용 여부는 따로 확인해야 합니다.

## 처리 과정 {#procedure}

1. Intent·Plan을 모델 계약으로 파싱하고 알 수 없는 필드와 잘못된 값을 거부합니다.
2. Plan 스키마는 image_tag=app:<source_revision>, 서비스 이름 중복 없음, 공개 HTTP 정확히 하나를 요구합니다.
3. worker는 명령이 있고 비공개이며 port/health가 없어야 합니다. HTTP는 유효 포트와 /로 시작하는 health 경로가 필요합니다.
4. Local/AWS별 DB·저장 타입, 로그, STORAGE_DRIVER 및 DB 사용 시 DATABASE_URL 이름 조건을 확인합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| schema_invalid | BLOCK | validate_plan 내부 모델 계약 위반 | 서비스·대상·저장·이미지 태그를 계약에 맞게 수정합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

성공 파싱 뒤 source_revision·target, 실행 binding의 intent_digest·plan_digest를 남깁니다. 실제 네트워크 관측은 없습니다.

## 해결과 재검증 {#remedy}

1. Plan의 대상과 서비스 공개 설정부터 확인합니다.
2. 분석이 맞으면 Planner 출력과 생성 로직을 수정합니다.
3. L-001 뒤 L-002와 G-003을 함께 통과해야 실행할 수 있습니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 공개 web 하나와 비공개 worker | PASS |
| 위반 | 공개 worker 또는 공개 HTTP 둘 | BLOCK |
| 경계 | HTTP port=65535 | 스키마 범위 안; demo 프로필은 3000 요구 |
| 오류 | 모델 파싱 이전 호출부 예외 | 그 호출 단계 오류; 이 규칙 실행을 꾸며내지 않음 |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.
