# G-002 · 지원 소스와 분석 일치

정책 1.0.0

## 목적 {#purpose}

검토하지 않은 실행 소스나 demo 앱과 다른 AI 분석이 배포 경로에 진입하는 것을 막습니다.

## 입력과 적용 조건 {#inputs}

Intent, 수집된 snapshot, RepoMap commit/tree와 호스트의 demo-profile을 사용합니다. 실제 배포 분석 뒤, 일반 Intent 검사 전에 실행합니다.

## 처리 과정 {#procedure}

1. 스냅샷과 매핑을 읽고 worker.js 존재에 따라 필수 파일 해시 집합을 선택합니다.
2. 필수 실행 파일의 해시를 비교합니다. src/prisma 아래 추가 파일과 허용 밖 실행·빌드 파일을 거부합니다. 문서 확장자도 위치에 따라 허용되지 않습니다.
3. package 이름·실행 scripts·정확한 dependencies/devDependencies를 비교합니다. test script는 실행 scripts 비교에서 제외합니다.
4. 분석의 commit·앱 이름·미해결 요구·서비스·상태·비밀 이름·일반 설정을 demo 계약과 대조합니다.
5. 인용 파일이 승인된 소스 집합에 속하고 인용 줄이 존재하며 비어 있지 않은지 검사합니다.

## 판정 기준과 사유 {#decisions}

| 사유 코드 | 현재 판정 | 발생 조건 | 확인과 조치 |
|---|---|---|---|
| unreviewed_runtime_source | UNSUPPORTED | 파일 해시·패키지·추가 파일이 검토 프로필과 다름 | 차이를 검토하고 지원 소스를 사용합니다. 해시 목록에 무조건 추가하지 않습니다. |
| intent_source_mismatch | BLOCK | 분석의 실행 필드가 프로필과 다름 | 당시 소스와 분석을 대조하여 누락·오분석을 수정합니다. |
| non_source_evidence | BLOCK | 문서 등 승인된 실행 소스 밖 인용 | 실제 소스 근거를 확인합니다. |
| invalid_source_evidence | BLOCK | 범위 밖 또는 빈 줄 | 유효하고 관련 있는 인용으로 분석을 다시 생성합니다. |

위 조건을 모두 만족하면 해당 규칙 PASS입니다. 전체 배포 성공을 뜻하지 않습니다. 앞선 규칙에서 중단되면 NOT_RUN이며, 적용 제외는 명시된 조건에서만 NOT_APPLICABLE로 남습니다. [공통 오류 분류](../results.md#classification)도 확인하세요.

## 근거 읽기 {#evidence}

source_revision·file_count를 기록합니다. 불일치 필드 정보가 예외에 있더라도 현재 규칙 결과에 모두 보존되는 것은 아닙니다.

## 해결과 재검증 {#remedy}

1. 소스 commit과 수정 파일을 확인합니다.
2. 지원 소스이면 분석 오류를 수정하고, 실제 소스 변경이면 지원 검토 대상으로 분리합니다.
3. 소스 단계부터 새 검사하여 Intent·Plan 단계까지 통과하는지 확인합니다.

[실패에서 다시 시작하는 방법](../troubleshooting.md#restart)을 참고하세요. 보존 자료 재검사는 원본 입력을 고치거나 새 소스를 가져오지 않습니다.

## non_source_evidence 해결 {#non-source-evidence}

이 코드는 인용 파일이 승인된 근거 소스 집합 밖에 있다는 뜻입니다. 파일이 실제로 없어도 발생하지만 README나 package-lock.json처럼 존재해도 근거로 허용하지 않는 파일일 수 있습니다. 스냅샷에 포함될 수 있는 파일과 분석 근거로 인용할 수 있는 파일은 같은 목록이 아닙니다.

1. 실패 기록의 source_revision과 수집 당시 snapshot·Intent를 확보합니다. 현재 브랜치 파일로 과거 인용을 추정하지 않습니다.
2. workloads와 state의 evidence를 모두 확인합니다. 현재 G-002 결과에는 source_revision·file_count만 남고 문제 인용 자체는 저장되지 않으므로, 결과만으로 어느 인용이 잘못됐는지 확정할 수 없습니다.
3. 해당 요구를 뒷받침하는 승인 소스의 실제 줄로 분석을 다시 생성합니다. 지원 파일 목록에 임의로 파일을 추가하거나, 요구와 무관한 줄로 바꾸지 않습니다.
4. 새 입력으로 G-002부터 다시 실행하고 I-001의 파일·줄 존재 확인 및 I-003·I-004·I-002의 관련성 검사까지 확인합니다. 소스가 바뀌었다면 새 commit의 지원 여부부터 확인합니다.

일반 배포 경로에서는 G-002가 먼저 실패하여 이후 Intent·Plan·패치·빌드로 진행하지 않습니다. 일반 Intent 검사 함수를 단독 호출한 사례의 evidence_file_missing과 혼동하지 마세요. [기록을 따라가는 예시](../logs.md#walkthrough)와 [재실행 동작](../troubleshooting.md#actions)을 참고하세요.

## invalid_source_evidence 해결 {#invalid-source-evidence}

인용 파일은 승인 집합 안이지만 줄 번호가 파일 끝을 넘거나 해당 줄이 공백뿐인 경우입니다. 파일:양의 줄번호 형식 자체가 잘못된 경우는 앞선 스키마 파싱의 실패이므로 이 사유로 단정하지 않습니다.

1. Intent가 인용한 파일을 동일 snapshot에서 열고 줄 번호와 내용을 대조합니다. 줄 번호는 1부터 셉니다.
2. 범위 밖·빈 줄이면 실제 요구를 설명하는 줄을 확인해 분석을 다시 생성합니다. 줄 이동의 원인이 소스 변경이면 source_revision도 새 소스와 일치해야 합니다.
3. G-002와 후속 Intent 검사를 새로 실행합니다. 존재하고 비어 있지 않다는 것만으로 해당 줄이 모든 요구를 증명하지는 않습니다.

보존된 잘못된 Intent를 그대로 재검사하면 같은 실패가 반복됩니다. 과거 context나 판정 행을 수정하지 않습니다.

## 검증 사례 {#cases}

| 종류 | 입력 또는 상황 | 기대 결과 |
|---|---|---|
| 정상 | 검토된 v1/v2 소스와 일치하는 분석 | PASS |
| 위반 | 저장 요구·비밀 이름 등의 분석 누락 | BLOCK |
| 경계 | 실행 파일에 주석 추가 | UNSUPPORTED |
| 오류 | 입력 스키마/스냅샷 처리 예외 | 예외 종류에 따라 고정 코드 ERROR; 성공으로 대체 안 함 |

위 표는 동작 설명입니다. 자동 재현한 범위와 테스트 연결은 아래 근거 및 [검증 사례집](../cases.md#reproduced)에서 구분합니다.

## 한계와 관련 검사 {#limits}

임의 앱 분석 기능이 아니라 검토된 demo 프로필 경계입니다. 주석 변경도 해시 차이로 미지원될 수 있습니다. test script 제외는 모든 npm 스크립트가 안전하다는 뜻이 아니며 Builder의 실제 실행과 별도로 확인해야 합니다.
