# 업그레이드 안내

## legacy에서 1.0.0

기존 판정은 보존합니다. 운영 배포의 보존된 입력과 이미지 식별값을 확보할 수 있으면 자동 재검사하고 배포별 운영자 검토를 요구합니다. 자료가 없으면 재검사 불가로 표시합니다.

## 여러 버전 건너뛰기

현재 정책부터 목표 정책까지의 변경 명세를 누적합니다. 중간 필수 조치를 생략하지 않습니다. 명세가 없거나 적용 여부를 모르면 확인 필요입니다.

## 재검사·검토·재배포

재검사는 모델 호출·빌드·배포 없이 보존 입력을 검사합니다. 검토는 특정 검사 실행과 정책에 연결되며 위반을 면제하지 않습니다. 메이저 전환은 전체 필수 검사와 배포별 검토가 필요합니다.

결과물 변경이 필요 없으면 재배포하지 않습니다. 필요한 경우 동일 commit으로 새 배포를 만듭니다. 소스 수정이 필요하면 새 commit의 일반 배포를 수행합니다. 기존 서비스는 자동 중단하지 않습니다.


## 1.0.0·강화 전 1.1.0에서 직접 근거 확인 {#evidence-hardening}

1. 배포 당시 정책 버전·식별값과 보존된 Intent·소스를 확인합니다. 같은 1.1.0 번호라도 규칙 정의와 식별값이 다르면 변경 비교가 필요합니다.
2. DB 사용 소스에는 I-003, worker 사용 소스에는 I-002의 변경을 적용합니다. worker 없는 V1은 I-002 권고 대상이 아닙니다. 입력이 없거나 무결성을 확인할 수 없으면 확인 필요로 남습니다.
3. 보존 자료 재검사는 원본 소스·Intent를 그대로 사용합니다. 모델 호출·빌드·서비스 배포·분석 수정은 하지 않습니다.
4. 직접 근거가 충분하면 새 정책의 검사 결과를 확인합니다. 부족하면 원래 PASS를 유지하고 새로운 BLOCK과 보완 권고를 함께 봅니다. 서비스 상태는 별도이며 정책 업데이트 때문에 서비스를 자동으로 중단하지 않습니다.
5. 근거 보완은 후속 정상 분석·배포에서 수행합니다. 새 검사·소스·필수 규칙 통과를 확인하고 원인 검토의 해결 검사 ID에 연결합니다. 과거 receipt나 판정 행을 수정하지 않습니다.

기존 자동 수정 전환에 필요한 검토 등 다른 변경 사유는 함께 표시합니다. 근거 강화에 따른 권고와 그 사유를 섞지 않습니다. 운영자의 확인만으로 BLOCK·ERROR를 PASS로 바꿀 수 없습니다. 같은 소스 재배포 버튼이 잘못된 보존 Intent를 고쳐주는 기능은 아닙니다.

## 검증 예시를 읽는 방법 {#examples}

배포 영향에서 운영 기록과 ‘정책 검증 예시’를 명시적으로 선택합니다. 기본은 운영 기록입니다. 예시는 이전 정책 검사기를 고정된 1.0.0 기준 commit에서 별도 실행한 결과와 현재 검사기의 결과를 비교하며, 과거 버전 이름만 바꿔 붙이지 않습니다.

정책 판정은 실제 검사 결과이고 배포 문맥은 모의입니다. 서비스 실행은 확인하지 않습니다. AI 응답 재생과 실제 모델 호출 여부도 별도 기록합니다. 예시에서는 재검사·검토·재배포 쓰기 동작을 제공하지 않습니다. 예시가 없거나 조회에 실패하면 새로 성공 결과를 만들지 않습니다.
