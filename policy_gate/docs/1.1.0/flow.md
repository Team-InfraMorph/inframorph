# 전체 실행 흐름과 중단 범위

## 최초 배포의 흐름 {#pipeline}

```text
소스 수집 → Analyzer가 원본 요구를 Intent로 생성
  → 대상별 G-002 → 대상별 Intent 검사
    I-000 → I-001 → I-006 → I-003 → I-004 → I-002
  → Planner가 대상 설계 생성 → Local/AWS G-003 → L-001 → L-002
  → 공통 준비 완료 → 필요한 구조 변경 승인
  → Local이 포함된 복수 대상이면 Local을 먼저 실행
    패치 생성 → P-001 → P-006 → P-007 → P-002 → P-003 → P-004 → P-005
    → 빌드 직전 패치 재검사 → X-001 → 이미지 빌드 → 실행·테스트
  → Local 상태가 LIVE일 때 AWS·온프레미스 실행 시작
    AWS: 자체 패치·검사·빌드·Adapter 실행
    온프레미스: Local에서 검증한 이미지와 구성을 원격 Docker에 전달
  → 대상별 상태와 조종실 접속 확인 결과 표시
```

소스·Intent·Plan의 공통 준비는 `LocalRuntime.analyze`에서 수행합니다. 규칙 ID 순서와 실행 순서는 다릅니다. Local/AWS worker 내부의 소스·분석·설계·패치 재검사는 각 경계에서 반복됩니다. snapshot 검증·모델 파싱·판정 저장 같은 규칙 밖 경계에서 실패하면 규칙 기록이 없을 수 있습니다.

## 대상별 중단 범위 {#targets}

| 지점 | 입력과 전달 자료 | 실패 시 영향 | 다시 확인할 작업 |
|---|---|---|---|
| 공통 분석·설계 준비 | snapshot·RepoMap → 검증된 Intent·대상 Plan | 선택한 대상의 worker 시작 전 전체 준비 중단 | 원본과 분석·설계를 확인한 뒤 새 정상 배포 |
| Local과 다른 대상 함께 선택 | 보존 context → 패치·빌드·Local 테스트 | Local이 LIVE가 아니면 AWS·온프레미스 명령을 호출하지 않고 실패 상태 기록 | Local 첫 실패 해결 후 새 실행 |
| Local 단독 또는 AWS 단독 | 선택한 대상의 입력과 검사 | 해당 실행의 후속 단계 중단 | 해당 대상의 첫 실패 해결 |
| Local 통과 뒤 AWS·온프레미스 | 각각의 Adapter 입력 | 두 대상은 동시에 실행되며 한쪽 실패가 다른 쪽의 성공을 자동 취소하지 않음 | 대상별 결과와 전체 상태를 함께 확인 |
| 빌드 | 검증된 패치 바이트 → 이미지 식별값 | 이미지 생성 또는 후속 실행 불가 | 패치·프로필·Builder 환경 확인 |
| 실행·접속 확인 | 이미지와 대상 환경 → 관측 결과 | 환경 실패·복구 기록 확인; 정책 위반으로 자동 분류하지 않음 | 실행 테스트와 조종실 직접 확인을 구분 |

현재 런타임은 온프레미스 선택 시 Local도 요구합니다. Local 선행 조건은 orchestrator가 기록한 `LIVE` 상태입니다. 별도로 저장하는 조종실 HTTP 직접 확인이 이 상태를 대신하지 않습니다. 정책 PASS만으로 다른 대상이 시작되는 것도 아닙니다.

## 온프레미스에서 확인된 범위 {#onprem}

온프레미스에도 공통 G-002·Intent 검사 기록은 남습니다. 실행은 Local에서 검증한 이미지·구성을 재사용합니다. 이것을 온프레미스 전용 18개 규칙의 독립 검사 완료로 표시하지 않습니다.

1.0.0의 변경 영향 명세는 Local/AWS를 대상으로 합니다. 온프레미스는 `target_scope_requires_review`로 확인 필요이며, 대상 전용 보존 자료(receipt)가 없어 정책 업데이트 재검사는 `UNAVAILABLE`입니다. 이 결과만으로 이미 실행 중인 서비스를 중단하지 않습니다. 원격 서버의 현재 공개 범위나 상태는 저장 자료의 정책 검사로 증명하지 않습니다.

## 같은 앱을 두 시점에 검사하는 이유 {#checkpoints}

| 시점 | 읽는 자료 | 기대 조건 |
|---|---|---|
| 분석 검사 | 원본 SQLite datasource와 Intent | Intent도 원본 DB를 sqlite로 설명해야 함 |
| 설계 검사 | 검사된 Intent와 대상 Plan | 원본 요구를 만족하는 PostgreSQL 서비스·설정·비밀정보 연결 |
| 패치 검사 | 원본·Plan·변환 bundle | provider는 postgresql로 변환하되 모델 구조와 무관한 앱 기능은 보존 |
| 빌드 직전 | 동일 snapshot·bundle과 최종 파일 | 승인한 패치와 실제 빌드 입력이 일치하고 X-001 프로필을 충족 |
| 실행 이후 | 실행 이미지·테스트·접속 결과 | 실제 동작은 별도 관측; 정책 통과와 동일한 결과가 아님 |

따라서 원본이 SQLite인데 Intent를 PostgreSQL로 바꾸는 것은 해결이 아닙니다. PostgreSQL은 이후 Plan과 승인된 패치에서 등장합니다. 같은 규칙도 실행 ID와 checkpoint가 다르면 별도 검사이며 이벤트 수는 규칙 종류나 배포 횟수가 아닙니다.

## 실패·복구·재검사의 차이 {#recovery}

- 첫 검사 예외 이후 남은 규칙은 NOT_RUN입니다. 별도 악성 행위 판정이 아닙니다.
- Local 실행 검증 실패 뒤 복구는 원인 분석·수정 후보·정책 검사·빌드·재검증을 다시 수행할 수 있습니다. 초기 정책 차단을 면제하지 않습니다.
- 정책 업데이트 재검사는 보존 snapshot·Intent·Plan·bundle·이미지 식별 연결을 검사합니다. 모델 호출·빌드·재배포·현재 클라우드 조회는 하지 않습니다.
- 자료가 없거나 변했다면 재검사 불가입니다. 최신 branch로 바꾼 결과를 과거 배포 결과로 쓰지 않습니다.
- 문서 갱신이나 재검사 실패만으로 기존 서비스를 자동 중단하지 않습니다.

## 규칙 밖 경계 {#boundaries}

필수 판정 저장 실패는 다음 실행을 막습니다. 진단 로그 저장 실패는 별도 경고입니다. snapshot/patch/image fingerprint, 정책 guard, 소스·artifact schema 실패를 규칙 내부 판정과 구분합니다. 기록이 없으면 성공으로 추정하지 않습니다.

## 직접 근거 실패의 중단 범위 {#evidence-hardening}

G-002가 원본과 요구사항을 확인한 뒤 I-003은 DB 직접 선언을, I-002는 worker 명령과 시작점 인용을 확인합니다. I-003이 먼저 실패하면 뒤의 I-004·I-002는 NOT_RUN입니다. 두 근거가 모두 부족해도 실행하지 않은 worker 검사를 통과·차단한 것으로 만들지 않습니다.

새 배포에서는 허용된 근거 보완 후보만 받아 같은 G-002·Intent 검사를 다시 수행합니다. 수정 전후 소스와 정책 식별값이 같아야 합니다. 전체 Intent 필수 검사 통과 전에는 Planner로 진행하지 않습니다. 공유 분석 단계가 실패하면 해당 새 배포의 대상별 후속 설계·빌드가 시작되지 않습니다.

과거 배포의 정책 재검사는 보존 자료를 그대로 검사하고 원래 PASS와 분리한 현재 결과를 남깁니다. 보완 권고가 생겨도 실행 중 서비스를 중단하지 않으며 자동 수정·빌드·배포를 시작하지 않습니다.
